## Bump mechanics (m114 → M138)
- **Sync:** a checkout synced without `-D` keeps stale m114 toolchain dirs
  (`buildtools/third_party/libc++abi/trunk`, `libunwind/trunk`, `clang_format/script`, "no longer
  part of this client"). Harmless — gn uses the new DEPS paths. `gclient sync -D` removes them.
- **Build:** uses **siso** (Chromium's newer executor) under `autoninja`. From-scratch ~1h40m on 32
  threads. content_shell = 1.4 GB unstripped.

## Build system
- `scripts/gen.sh` runs `cobalt/build/gn.py --no-rbe -p chromium_linux-x64x11 -c <devel|qa> out/<preset>`
  (`deck` → `qa`, other presets → `devel`, `gold` only for `scripts/release.sh`), then appends
  `args/common.gn` + `args/<preset>.gn` to `args.gn` and re-runs `gn gen`. Our args files hold only
  overrides of Cobalt's platform config, never a full arg set.
- The runnable target is `content_shell`, built with `autoninja` (siso underneath).

## youtube.com/tv page constraints
The page ships `require-trusted-types-for 'script'`: a bare `innerHTML`/`outerHTML`/
`insertAdjacentHTML` assignment throws and renders nothing, silently from the launcher's side.
`textContent`, `setAttribute` and CSSOM writes are not gated by Trusted Types. No `trusted-types`
allowlist is pinned, so any policy name is accepted (our scripts create `deckback`). Inline `<style>`
blocks and `style` attributes are dropped by the CSP; use `adoptedStyleSheets` or
`el.style.setProperty` (`../durable/self-update.md` ★ RENDER FIX). Re-check the CSP header on each
bump: an allowlist would make policy creation throw.

## Media & VA-API (S0.5) — hardware decode ships
`config/app.json:cobalt_flags` carries `--enable-features=VaapiVideoDecodeLinuxGL --use-angle=gl`.
Both are required: `--use-angle=gl` alone gets VA-API but the feature flag selects the decoder; the
feature flag alone leaves ANGLE on Vulkan/radv and silently falls back to software. The same flags
painted green-band corruption on every frame on m114 (`../durable/hardware.md`); M138's ANGLE imports
the tiled NV12 VA surface correctly.

Verified on-Deck (OLED, Game Mode, real Leanback VP9 playback) under the mandatory DUAL gate:
- decoder = `VaapiVideoDecoder`, `kIsPlatformVideoDecoder=True` (via deckctl + a single-connection capture)
- pixels = **0.0% green-band rows** across 5 sampled frames, visually confirmed clean
  (`tests/deck/lib/probes.py:video_corruption_verdict`, PIL, L0-tested) — 2026-07-10.
- Re-confirmed 2026-10-21 by the L2 gates `test_hardware_decode_is_vaapi` + `test_video_is_not_corrupt`
  on a build carrying the slim args.

To test engine flags without a rebuild:
`flatpak override --user --env=DECKBACK_EXTRA_ARGS='…'` (the launcher appends it to the engine argv).

**P4 power (OLED, on battery, under `VaapiVideoDecoder`, P = V×I — no power_now node):** two runs on
2026-07-10 — `just power` averaged **5.6 W** (the figure quoted elsewhere) and `just power 120`
averaged **5.91 W** over 120 samples; both PASS vs ≤9 W, with playback confirmed before and after. A
2026-10-21 run read **6.39 W** (PASS) on a different video, brightness and SteamOS 3.8.28 — not
comparable to the 2026-07-10 runs. LCD unit unknowable.

No `--ignore-gpu-blocklist` or `VaapiIgnoreDriverChecks` is needed; they would only suppress real
driver checks.

Gotcha for any decoder probe: a CDP client MUST call `cdp.enable_media()` or the Media domain never
streams `kVideoDecoderName` and the decoder reads as None (a broken probe, not software decode).
`SystemInfo.getInfo` → `gpu.videoDecoding` is not a decode signal either: it is the legacy VDA profile
list and read empty while VA-API was decoding on M114 (unverified on M138). The Media domain's
`kVideoDecoderName`/`kIsPlatformVideoDecoder` on a live player is the signal.

## Widevine (S0.3)
Library-CDM path intact. The Widevine CDM registration patch needed a SINGLE API-drift fix at this
pin: the capability header moved `media/cdm/cdm_capability.h` → **`media/base/cdm_capability.h`**.
Everything else is source-compatible: `CdmInfo`'s 8-arg ctor now takes
`std::optional<media::CdmCapability>` (implicit conversion from `CdmCapability` works),
`ContentClient::AddContentDecryptionModules` virtual signature is unchanged, `CdmHostFilePath` still
in `media/cdm/cdm_host_file.h`. Compiles clean. Untestable without a real CDM: `CdmCapability`
gained a `version` field; the ctor comment says capability.version overrides the passed version, and
`WidevineL3Capability()` leaves it empty — harmless until a CDM is actually loaded (never in CI).
